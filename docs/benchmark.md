### ROCm 阻塞详情

安装 `sd-cpp:rocm` 下载 5.2GB / 耗时 17.6 分钟后失败：

```
Error: TheRock extraction failed: bin directory not found
```

这是 **lemonade-sdk 上游的 ROCm 包分发 bug，非本机硬件问题**。佐证：
- [issue #2722](https://github.com/lemonade-sdk/lemonade/issues/2722)（open）报告者为 Ryzen AI Max+ 395 / gfx1151，**不同芯片、同一故障**
- [issue #1902](https://github.com/lemonade-sdk/lemonade/issues/1902)、[#1807](https://github.com/lemonade-sdk/lemonade/issues/1807) 为同类 ROCm 下载/版本问题
- CLI 无版本锁定参数可绕过

AMD 官方 Windows 支持矩阵中 gfx1102 的 Runtime 与 HIP SDK **两栏均为全支持**，所以硬件侧没有障碍，等上游修复即可重测。

## 三、快速高分辨率路径（关键发现）

同为产出 2048×2048：

| 方案 | 耗时 | AMD 显存峰值 |
|---|---|---|
| 直接生成 2048² | 483.64s | 6.66 GB |
| `--hires --hires-scale 2.0`（1024→2048） | 536.04s | 6.66 GB |
| **512² 出图 + RealESRGAN 4× 纯超分** | **24.25s** | **0.85 GB** |

- `--hires` **不省时间**：它在放大后还要跑第二轮完整去噪，成本与直出相当，其价值在构图质量而非速度。
- **纯超分快约 20 倍**，且显存占用极低。画质上 ESRGAN 有轻微塑料感、背景细节被涂抹，但主体锐利，多数用途够用。

命令：

```bash
# 1) 快速出图
sd-cli -m <sd_turbo.safetensors> -p "<prompt>" -H 512 -W 512 -o base.png --vae-tiling --diffusion-fa

# 2) 纯超分 4x
sd-cli -M upscale --upscale-model <RealESRGAN_x4plus.pth> -i base.png -o out2048.png
```

## 五、双卡拆分：验证为负面结果，已回滚

sd-cli 支持按组件分派设备：`--backend clip=...,vae=...,diffusion=...`

ggml 设备编号（**注意顺序**）：
```
vulkan0 = Intel Arc Graphics    (uma:1, matrix cores: none)
vulkan1 = AMD RX 7600M XT       (uma:0, bf16:1, matrix cores: KHR_coopmat)
```

把 CLIP+VAE 甩给 Intel 核显、扩散主干留在 AMD，服务端实测**全面变慢**：

| 分辨率 | 全 AMD | 双卡拆分 | 结果 |
|---|---|---|---|
| 512² | 2.47s | 7.55s | 慢 3.1× |
| 1024² | 10.93s | 39.42s | 慢 3.6× |
| 2048² | 73.22s | 199.17s | 慢 2.7× |
| 2816² | 319.76s | 471.59s | 慢 1.5× |
| 3072² | 失败 | 失败 | 天花板未改善 |

原因：服务端模型常驻本就不抖动，跨设备传输纯属额外开销；Intel 核显无矩阵核心，
承接任何计算都是拖累。3072 仍失败也说明瓶颈在 AMD 上的扩散主干分配，与 CLIP/VAE 无关。

**结论：单个扩散任务不要拆分，已回滚为全 AMD。**

> 方法论教训：最初用 sd-cli 直调测得拆分"快 5.2 倍"（414s→80s），是错误结论。
> 那是 CLI 冷加载路径撞显存墙的特例。发现服务端实际传了 `--vae-tiling --diffusion-fa`
> 而我的 CLI 命令漏了，补上后重测才得到真实结论。**测性能前必须先对齐两条路径的参数。**

## 六、`enable_dgpu_gtt` —— 千万别开（58 倍性能塌陷）

为尝试突破 3072 天花板而开启 `enable_dgpu_gtt=true`，结果：

| 配置 | 512² 连续出图 |
|---|---|
| `enable_dgpu_gtt=false` | **2.73 s** |
| `enable_dgpu_gtt=true` | **158 s** |

GTT 允许驱动把缓冲放进系统内存，而 eGPU 经雷电总线访问系统内存极慢。
**而且它并没有解决天花板**：开启后 3072² 依旧失败。

天花板的真正原因是**单次分配上限**，不是显存总量：

```
ggml_vulkan: Device memory allocation of size 5368709120 failed
```

`5368709120` = 正好 **5 GiB**，Vulkan 单块缓冲的硬上限。GTT 能扩总池，改不了这个。

> 这个坑还污染过一轮测量：开着 GTT 时测出的双卡拆分数据全部作废，
> 关掉后重测才得到第七节的正确结论。**测性能前先确认没有残留的实验性开关。**

## 七、模型组合：真正的甜点

服务端每配置前重启，消除状态残留后的干净数据（512² 出图 + 8B/3B 对话交替）：

| 配置 | 连续 chat | 连续 img | 交替 chat/img | 交替一轮合计 |
|---|---|---|---|---|
| A 全 AMD，max=1 | 3.0–3.6s | **2.8–3.0s** | 10.6s / 2.6s | **13.2s** |
| B 全 AMD，max=2 | 3.1–3.2s | 2.8–3.1s | 11.9s / 2.5s | 14.5s |
| C LLM@AMD + 图@Intel | 3.1–6.5s | 13.2–14.0s | **4.5s** / 14.9s | 17.9s |
| **D 换 3B 模型，全 AMD** | — | — | **2.1s / 2.5s** | **4.6s** |

结论：

1. **拆到两块卡（配置 C）在所有场景都是负优化。** 它把交替 chat 从 10.6s 压到 4.5s，
   但出图从 2.6s 涨到 14s，净亏。Intel 核显无矩阵核心，接任何计算都是拖累。
2. **`max_loaded_models=2` 无效**（配置 B ≈ A）。因为 8B(5.6GB) + SD-Turbo(3.7GB) = 9.3GB
   **装不进 8GB**，两个模型根本没能共存。
3. **真正的甜点是换小模型（配置 D）**：3B + SD-Turbo 交替一轮仅 4.6s，比 8B 方案快 **2.9 倍**。

   但要如实说明机制：`max_loaded_models` 设 1 或 2 结果完全相同，
   `lemonade status` 始终只显示 SD-Turbo 驻留——**两模型仍未真正共存**，
   收益纯粹来自 3B 换入换出便宜（约 2s vs 8B 的约 10s），不是共驻留。

> 后续被第十二节推翻：3B 不是最优小模型，Gemma-4-E2B 在各方面都更好。

## 十一、上下文长度与 KV cache 量化

8B 模型（Q4_1）：

| ctx_size | AMD 显存 |
|---|---|
| 4096（默认） | 5.39GB |
| 16384 | 6.25GB |
| **32768** | **6.39GB** |

**默认 4096 太保守，开到 32768 只多花 1GB。**

KV cache 量化实测**零收益**：

| 配置 | 显存 |
|---|---|
| 默认 | 6.46GB |
| `-fa on` | 6.47GB |
| `-fa on -ctk q8_0 -ctv q8_0` | 6.46GB |

已抓 llama-server 命令行核实参数确实传入，但无任何变化。原因未查明，记为负面结果。

`GGML_VK_FORCE_MAX_ALLOCATION_SIZE` 同样无用——uint32 上限约 4GB，
只能把限制调低，无法突破已有的 5 GiB。

## 十一之二、SDXL vs SD-Turbo：画质换速度

| 模型 | 分辨率 | 耗时 | 显存 |
|---|---|---|---|
| SD-Turbo | 512² | 3.26s | 4.21GB |
| SDXL-Base-1.0 | 512² | 14.81s | **7.14GB** |
| SDXL-Base-1.0 | 1024² | 60.99s | 7.15GB |

SDXL 慢 4.5 倍、显存多 2.9GB，但**画质明显更好**：真实光影、自然景深、
连贯木纹，明显更接近摄影。SD-Turbo 是单步蒸馏模型，胜在快。

**顺带订正一则流传的说法**：网上常说「SDXL 在 AMD 上需要 8GB 以上显存」，
本机实测 **7.14GB 即可跑通** 1024²，8GB 卡是够的（但余量很小）。

补测 **SDXL-Turbo** 后结论要修正——它才是画质档的正确选择：

| 模型 | 512² | 1024² | 显存 |
|---|---|---|---|
| SD-Turbo | 3.26s | 10.93s | 4.21GB |
| SDXL-Base-1.0 | 14.81s | 60.99s | 7.14GB |
| **SDXL-Turbo** | **3.90s** | **15.96s** | 7.14GB |

SDXL-Turbo 提供 SDXL 级画质，但只要 SDXL-Base **约 1/4** 的时间。
瑕疵：偶见构图重影（如壶盖出现两个）。

**选型**：
- 批量/迭代、显存吃紧 → **SD-Turbo-GGUF**（2.52GB，最快）
- 追求画质 → **SDXL-Turbo**（7.14GB，8GB 卡余量很小）
- SDXL-Base-1.0 没有使用理由，被 SDXL-Turbo 全面压制

⚠️ **SDXL 系列不要走 `quick-image.ps1` 的 CLI 路径**：实测 512² 需 825.9s，
而同样一张经服务端 API 只要 14.8s（56 倍差异，原因未查明）。

## 十二、最终甜点组合（本项目最重要的结论）

每配置前重启服务，512² 出图 + 对话交替：

| 组合 | 交替 chat | 交替 img | 一轮合计 | AMD 显存 |
|---|---|---|---|---|
| 8B + SD-Turbo（旧最优） | 14.6–15.5s | 3.7–4.2s | ~19s | 7.18GB + **3.22GB 溢出** |
| **E2B + SD-Turbo-GGUF** | **0.27–0.60s** | **2.49–2.51s** | **~3.0s** | 5.68GB + 0.52GB |

**快 6.3 倍**，溢出从 3.22GB 降到 0.52GB —— 两个模型**这次是真正共存了**。

这才是 8GB 卡的正确用法：**不是把任务拆到两块卡，
而是把模型缩到能在一块快卡上共存。**

## 十三、当前生效配置（最优）

```
sdcpp.backend      = vulkan
sdcpp.vulkan_args  = (empty)   # 双卡拆分已回滚，负优化
llamacpp.backend   = vulkan
max_loaded_models  = 1
ctx_size           = 32768     # 默认 4096 太保守，仅多花 1GB
enable_dgpu_gtt    = false     # 关键！设 true 会慢 58 倍
```

**Intel 核显的最佳角色不是分担计算，而是专心驱动显示**，
让 AMD 的 8GB 不被桌面合成占用。

快速出图脚本：`scripts/quick-image.ps1`（或 `npm run image`）

## 十四、Vulkan flash-attention：网上说的"AMD 上会退化"没有在这块卡上重现

外部调研翻出几个真实存在的 GitHub issue，说 llama.cpp 的 Vulkan flash-attention
在 AMD 卡上会**回退到 CPU**、导致 60-97% 的性能损失（RX 6700 XT、RX 7900 XTX/7800 XT，
`llama.cpp#12526` / discussion `#12629`）。这足够吓人，值得亲自测一遍再采信，
而不是直接把"AMD 上 FA 是坑"写进结论——上次犯过一次这种错（见"方法论教训"）。

实测（`llama-bench.exe -fa off,on`，同一个 8B Q4_1 模型，同一块 RX 7600M XT）：

| 长度 | FA off | FA on | 差异 |
|---|---|---|---|
| pp512 | 908.49 ± 2.13 | 903.75 ± 1.98 | 打平（噪声内） |
| tg128 | 40.99 ± 0.03 | 41.13 ± 0.16 | 打平（噪声内） |

**没有重现 issue 里说的灾难性回退。** 短上下文（512）两者打平；长上下文（4096）
FA 确实更慢，但只慢 9%，跟"回退到 CPU 导致慢 60-97%"完全不是一个量级。
最可能的原因：这些 issue 报的是更早期的 llama.cpp 版本，AMD 的 Vulkan FA 路径
后来被修过（这块卡的 `matrix cores: KHR_coopmat` 说明协作矩阵扩展是有的，
不是落到纯标量回退路径）。**结论：不要把这条社区结论直接抄进自己的配置建议——
在当前 build（`d6d899580`/9747）上，`-fa off` 对长上下文 pp 有小幅优势，
短上下文和 tg 基本不受影响，不是非黑即白的"AMD 上必须关 FA"。**
