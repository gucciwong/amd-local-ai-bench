# Vulkan-first，而不是 ROCm-first

## 在一块 8GB 的 AMD 移动显卡上，我全程没用上 ROCm，反而一切顺利

**结论先行**：如果你在 Windows 上用消费级 AMD 显卡跑本地 AI，
先试 Vulkan，别一头扎进 ROCm。本文所有数字都来自一次真实的逐项实测，
包括那些推翻了我自己前一个结论的数据。

**测试环境**

- AMD Radeon RX 7600M XT 8GB（gfx1102 / RDNA3），经 Thunderbolt 3 外接坞连接
- 主机 Intel Core Ultra + Arc 核显（所以这是一台"双显卡"机器）
- Windows 11，Adrenalin 32.0.21030.2001
- Lemonade Server 11.5.0

---

## 一、ROCm 这条路，在 Windows 上根本没走通

按 AMD 官方 skill 的推荐安装 ROCm 后端：

```
lemonade backends install sd-cpp:rocm
```

下载 5.2GB、耗时 **17.6 分钟**，然后：

```
Error: TheRock extraction failed: bin directory not found
```

我一开始怀疑是自己的硬件或 eGPU 有问题。查证后不是：

- AMD 官方 Windows 支持矩阵里，gfx1102 的 **Runtime 和 HIP SDK 两栏都是全支持**
- [lemonade-sdk#2722](https://github.com/lemonade-sdk/lemonade/issues/2722)（截至撰稿仍 open）
  报告者用的是 Ryzen AI Max+ 395（gfx1151）——**不同芯片，同一处失败**
- CLI 没有版本锁定参数可以绕过
- v11.5.0 已是最新版；讽刺的是 v10.8.0 的发布说明写着
  "enable TheRock ROCm installation on Windows for Radeon RX GPUs"

也就是说：**AMD 想支持，代码写了，但打包坏了，而且坏了至少两周没人管。**

这不是算力问题，不是驱动问题，是**分发问题**。

## 二、Vulkan 直接就能用，而且很快

同一台机器，`sd-cpp:vulkan` 安装耗时 **9.6 秒**。

出图（SD-Turbo，512²，20 步）：

| 后端 | 冷启动 | 热态 |
|---|---|---|
| CPU | 70.82s | 50.58s |
| **Vulkan** | 28.50s | **2.47s** |

热态下 **快约 20 倍**。

文本推理（llama.cpp Vulkan 后端）：

| 模型 | TPS | TTFT |
|---|---|---|
| Gemma-4-E2B | **55.6** | 128 ms |
| DeepSeek-Qwen3-8B | 33–34 | 156–455 ms |
| Gemma-4-12B | 6.9–12.3 | 935–2850 ms |

一块 8GB 的移动显卡，8B 模型稳定 33 tok/s。这个数字对日常使用完全够用。

**而且我确认过它真的跑在独显上**，不是悄悄落到核显：卸载模型时 AMD 专属显存
从 4.21GB 掉回 0.24GB，加载时爬回去——完整闭环。

## 三、为什么 Vulkan 在这个场景反而是更优解

**1. 它是驱动自带的。** `amdhip64_6.dll`（HIP 运行时）和 Vulkan 都随 Adrenalin
驱动安装，不需要额外装 HIP SDK。ROCm 需要的那一整套分发链，正是坏掉的那一环。

**2. 它跨厂商。** 同一份 Vulkan 代码在 Intel Arc 上也跑（本文的测试机两块卡
都被 ggml 枚举到了）。ROCm 只服务 AMD，而且只服务 AMD 支持列表里的型号。

**3. 硬件能力没有被浪费。** ggml 探测到的设备信息：

```
Vulkan0 = Intel Arc Graphics  | uma:1 | matrix cores: none
Vulkan1 = AMD RX 7600M XT     | uma:0 | bf16:1 | matrix cores: KHR_coopmat
```

`KHR_coopmat` 就是协作矩阵扩展，等价于张量核心。**Vulkan 用得到 RDNA3 的矩阵单元**，
不存在"必须上 ROCm 才能发挥硬件"的说法。

## 四、比后端选择更重要的：那些没人写下来的坑

坦白说，本次实测中造成性能差异最大的因素，**都不是后端选择**。

### 坑 1：`enable_dgpu_gtt=true` 慢 58 倍

这个开关看起来很美好——"让独显借用系统内存"。在 eGPU 上是灾难：

| 设置 | 512² 连续出图 |
|---|---|
| `false` | **2.73 s** |
| `true` | **158 s** |

而且它**并不能提高分辨率上限**。任何文档都没提这件事。

### 坑 2：显存争用会让性能塌到 1/34

sd-cli 与常驻的 sd-server 同时各要 6–7GB，8GB 卡直接崩：

| 场景 | SDXL 512² |
|---|---|
| 显存被占着 | 825.9 s |
| **清空后** | **24.1 s** |

这个坑还有个更阴险的副作用：**它让所有测量数据都不可信**。
本次调查中同一配置的出图耗时在 2.5s ↔ 158s 之间摆动过，全是这个原因。

### 坑 3：分辨率天花板不是显存不够

3072² 必失败，报错：

```
ggml_vulkan: Device memory allocation of size 5368709120 failed
```

`5368709120` 正好是 **5 GiB**——Vulkan 的单次分配上限。
我试过三种"扩显存"手段，全都无效：

- `enable_dgpu_gtt=true`（借系统内存）→ 3072 照样失败
- 换量化模型（省 1.6GB）→ 3072 照样失败
- `GGML_VK_FORCE_MAX_ALLOCATION_SIZE` → uint32 上限约 4GB，只能调低，没法调高

**总量和上限是两回事。** 错误信息里没有一个字提到这是"单次分配"限制。

## 五、双显卡不要拆分同一个任务

机器上有两块卡，很自然会想"分工"。sd-cpp 也确实支持
`--backend clip=...,vae=...,diffusion=...` 按组件分派设备。

**实测在所有场景都是负优化：**

| 分辨率 | 全 AMD | AMD 扩散 + Intel VAE/CLIP |
|---|---|---|
| 512² | 2.47s | 7.55s |
| 1024² | 10.93s | 39.42s |
| 2048² | 73.22s | 199.17s |

原因：核显没有矩阵核心，接任何计算都是拖累；跨设备传输是纯开销。

> 我第一次测这个时，得出的是"拆分快 5.2 倍"。那是错的。
> 原因是我直接调 sd-cli 时漏了服务端默认带的 `--vae-tiling --diffusion-fa`，
> 撞了显存墙。补上参数重测，方向完全反转。
> **教训：跨路径做性能对比前，先抓两边的真实命令行核对参数。**

**核显的正确角色是专心驱动显示**，让独显的 8GB 不被桌面合成占用。

## 六、8GB 卡的正确用法：缩模型，不是拆卡

真正让性能翻倍的，是模型选型：

| 组合 | 交替 chat | 交替 img | 一轮合计 | 显存溢出 |
|---|---|---|---|---|
| 8B + SD-Turbo | 14.6–15.5s | 3.7–4.2s | ~19s | **3.22GB** |
| **E2B + SD-Turbo-GGUF** | **0.27–0.60s** | **2.49–2.51s** | **~3.0s** | 0.52GB |

**快 6.3 倍**，因为两个模型这次真正共存了（5.68GB / 8GB），不再互相驱逐。

其他有用的选型结论：

- **量化版免费午餐**：SD-Turbo-GGUF 与原版**同速**，但省 1.6GB
- **SDXL-Turbo 取代 SDXL-Base**：同等画质，只要 1/4 时间（1024² 15.96s vs 60.99s）
- **高分辨率别直出**：512² 出图 + RealESRGAN 纯超分 = 24.25s，
  直接生成 2048² 要 483.64s（**快 20 倍**）。
  注意 sd-cpp 自带的 `--hires` 会再跑一轮完整去噪，**不省时间**（536.04s）
- **上下文可以放开**：8B 开到 32K 只多花 1GB（5.39→6.39GB），默认的 4096 太保守

## 七、给 AMD 用户的实际建议

1. **先装 Vulkan 后端**，跑通了再考虑要不要碰 ROCm
2. **`enable_dgpu_gtt` 保持 false**，尤其是 eGPU
3. **8GB 卡优先用 GGUF 量化模型**，是白捡的显存
4. **高分辨率走"小图 + 纯超分"**，不要直出也不要 hires
5. **别拆双卡**，核显去驱动显示
6. **做任何性能对比前先清空显存**，否则数据全是噪声

## 八、这件事的更大含义

整个过程里，卡住我的没有一件是"算力不够"或"缺算子"。

是打包坏了、是没人记录过那个开关是陷阱、是错误信息不说人话、
是两条执行路径的默认参数不一致、是网上流传的说法（"SDXL 需要 8GB 以上"）
和实测（7.14GB 就够）不符。

**AMD 的 AI 生态差距，很大一部分不在内核层，在集成、默认值和"经过验证的知识"这一层。**
而这一层不需要资本，需要的是在真机上把每条说法验一遍的耐心。
